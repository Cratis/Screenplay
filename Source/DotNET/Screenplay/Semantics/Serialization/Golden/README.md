# Golden vectors

Full ESM goldens pin canonical executable semantic model bytes and semantic revisions.
Keep full goldens for **v1–v7, v24, v27 and v28**. The legacy versions have thin or no
feature corpora; v24 has no checked-in feature-corpus ESM pin. V27 and v28 retain the
previous and current full vectors. Older versions v8–v23 and v25–v26 are pinned by
`Screenplay.CanonicalCorpus/Corpus/**/expected/esm-vN.json`, not cumulative full goldens.
Keep every feature corpus and every `esm-legacy.json` control.

When a new version lands, retain its full golden and the previous version's. Remove
an older full golden only once a checked-in feature corpus pins that version's bytes.
The version-matrix specs require a full golden or feature-corpus pin for all 28 declared
versions, and assert that population count explicitly.

## Consuming the vectors

Consume the released bytes through `Cratis.Screenplay.CanonicalCorpus`, rather than
copying these files. `EsmGoldenVectors.Versions` discovers only retained full vectors in
ascending order. `EsmGoldenVectors.Get(version)` returns an `EsmGoldenVector` with
`Version`, immutable `Bytes` and `SemanticRevision`, verified by the strict ESM reader.
Versions without a full golden throw `EsmGoldenVectorNotFound`; use their feature corpus
instead. `EsmGoldenVectors.PolicyNegationV7` exposes the separate v7 extension vector.
The package embeds these files in every build configuration, without copies.

| Full golden | Source model in `../given/canonical_serialization_golden_vectors*.cs` |
| --- | --- |
| `full-esm-v1.json` | `CreateSemanticModel()` — baseline portable model |
| `full-esm-v2.json` | `CreateSemanticModelV2()` — typed destinations and specification event sources |
| `full-esm-v3.json` | `CreateSemanticModelV3()` — implementation attachments |
| `full-esm-v4.json` | `CreateSemanticModelV4()` — multiple event generations |
| `full-esm-v5.json` | `CreateSemanticModelV5()` — keyed read-model absence |
| `full-esm-v6.json` | `CreateSemanticModelV6()` — triggers, reactions and captures |
| `full-esm-v7.json` | `CreateSemanticModelV7()` — generated properties, responses and fixtures |
| `full-esm-v24.json` | `CreateSemanticModelV24()` — cumulative model with first-class text rules |
| `full-esm-v27.json` | `CreateSemanticModelV27()` — flat composite read-model keys |
| `full-esm-v28.json` | `CreateSemanticModelV28()` — command Uuid equality |

Earlier builders still used by retained cumulative models or feature-refusal specs
remain available, but have no full-golden regeneration selector.

## Regenerating

Change the source model first. For the baseline v1–v7 goldens and the four sidecars:

```bash
SCREENPLAY_REGENERATE_GOLDEN=1 dotnet test Source/DotNET/Screenplay/Screenplay.csproj -c Debug
```

The `1` setting rewrites eleven files: v1–v7 and the four sidecars below. To regenerate
only one retained full golden, set `SCREENPLAY_REGENERATE_GOLDEN` to `2`, `3`, `4`, `5`,
`6`, `7`, `24`, `27` or `28` with the same command. Deleted versions have no selector
and are never regenerated. All supported modes deliberately fail with
`GoldenVectorsRegenerated`. Review the diff, rebuild embedded resources, then rerun
without the variable. Never edit generated bytes by hand.

Feature corpora have their own regeneration switches in their owning specifications;
`SCREENPLAY_REGENERATE_GOLDEN` does not rewrite them. Their expected ESM bytes and
semantic revisions are checked against equivalent compiled source forms and round trips.
Regenerate only the corpus whose source contract intentionally changed, review its diff,
rebuild and rerun without its switch. Published semantic versions remain frozen.

Regenerate the policy-negation extension independently of the original goldens:

```bash
SCREENPLAY_REGENERATE_POLICY_NEGATION=1 dotnet test Source/DotNET/Screenplay.CanonicalVectors.Specs/Screenplay.CanonicalVectors.Specs.csproj -c Debug -f net10.0 --filter FullyQualifiedName~for_PolicyNegationCorpus
```

This writes the extension golden and its corpus bytes/revision, then deliberately fails.
Review, rebuild and rerun without the variable.

## Separate serialization contracts

| File | Source |
| --- | --- |
| `full-expressions-v1.json` | `canonical_serialization_golden_vectors.CreateExpressions()` |
| `full-identity-catalog-v1.json` | `canonical_serialization_golden_vectors.CreateIdentityCatalog()` |
| `typed-contexts-v1.json` | `when_describing_typed_contexts.GoldenBytes()` |
| `unbound-handler-context-v1.json` | `when_describing_an_unbound_handler.GoldenBytes()` |

Expression and typed-context vectors are not ESM documents. The identity catalog has
its own catalog revision. The vectors project embeds the retained ESM goldens and the
sidecars except `full-expressions-v1.json`, and checks their serialization contracts.
An ESM serializer change can affect feature-corpus bytes and revisions too; release
`Cratis.Screenplay` and `Cratis.Screenplay.CanonicalCorpus` together when they change.
