## Context

[0025](0025-allocate-esm-v7-to-responses-and-number-later-versions-at-admission.md) item 2 protects published version numbers, including prereleases, but the version table still calls ESM v10 claimed and unreleased. Reaction system identity under [0043](0043-reaction-identity-runs-as.md) first shipped in Screenplay v4.125.0 ([PR #621](https://github.com/Cratis/Screenplay/pull/621)). [0063](0063-admit-production-routes-and-observer-filters-as-esm-v10.md) then extended v10 with production routes and observer filters in v4.129.0, on the mistaken premise that no v10 bytes had been released.

Consumers can already have admitted published v10 bytes. Treating publication and release-table maintenance as separate boundaries lets that contract change while its number stays fixed. Exact number literals (0064, [PR #641](https://github.com/Cratis/Screenplay/pull/641)) and [enum member numbers](0065-explicit-enum-member-numbers.md) need a settled boundary before their admission.

## Decision

An ESM version is published, released and frozen as soon as any NuGet or npm package exposing it is published, whether a release or a prerelease. From that publication onward, no extension may change the canonical bytes of a model that already bound: a change takes a new ESM version unless it qualifies as a byte-preserving extension under [0004](0004-admission-and-governance-of-portable-executable-semantics.md). This amends 0025 item 2. A claimed, unreleased entry exists only until its first publishing merge; in practice the admitting pull request's release moves it into the released table. New features take the next version at their release-ready admission checkpoint; one feature per version is fine. The already-shipped 0063 extension is a retroactive exception: its v4.129.0 bytes are now part of frozen v10, and consumers admitting v10 must take them as part of that contract.

### Amendment to 0025

Only item 2's publication boundary and the resulting table transition change. A version's number is still assigned at admission against current `main`; an open pull request or branch holds no claim; at most one genuinely unpublished claim exists; published numbers are never withdrawn, renumbered or reused. 0004's admission evidence and explicit consumer admission remain in force. 0025 stays accepted and its decision text is preserved, with a dated note pointing here.

### Retroactive exception for 0063

ESM v10 was published in Screenplay v4.125.0, not first released after 0063. The production-route and observer-filter bytes published in v4.129.0 remain v10. They are not removed, renumbered or regenerated by this record. The exception corrects the documented contract to match shipped packages; it is not permission for another byte-changing v10 extension. 0063 stays accepted and its original reasoning is preserved as history, with a dated note pointing here.

## Options considered

- **Freeze on first package publication (chosen).** It uses the moment consumers can obtain the contract, including prerelease consumers, rather than a later documentation update.
- **Freeze only when the released table is updated.** Rejected: consumers can have admitted a published package while the table still calls its ESM version unreleased.
- **Keep extending published v10 by claim.** Rejected: a number would no longer identify the contract a consumer admitted.
- **Move 0063's shipped bytes to a new version now.** Rejected: v4.129.0 already exposes those bytes as v10. A retroactive exception preserves that published contract without changing canonical bytes.
- **Batch every new feature into one later version.** Not required: features may be admitted and released independently, one version at a time.

## Default if unanswered

The stale table keeps v10 open to extensions despite its publication. Exact number literals and enum member numbers have no settled admission boundary, and a consumer's v10 admission can silently acquire a different byte contract.

## Timeline and scope

In force from acceptance on 2026-10-11 until superseded, before admitting exact number literals or enum member numbers. The 0063 exception applies retroactively to the v4.129.0 publication.

In scope: when an ESM version freezes, when a claimed entry becomes released, the shipped v10 exception, and the admission order of exact number literals and enum member numbers.

Out of scope: changing canonical or corpus bytes, changing version constants, admitting either pending feature, changing 0004's byte-preserving extension rule, or automatically admitting v10 in another consumer.

## Verification

**Done when:** the interoperability table lists v10 as released with all three selecting features; product documentation, MCP readiness and editor help no longer call v10 unreleased; 0025 and 0063 point to this amendment without rewriting their decisions; and no golden, corpus bytes or version constants change.

**Verify by:** the interoperability version-table specification, MCP reaction-identity readiness specifications, a search for v10 release wording outside decision history, and a diff confirming that canonical bytes and version constants are untouched.

## Consequences

A published version has one frozen contract. Consumers admitting v10 must include reaction system identity, production routes and observer filters, including the 0063 bytes. A consumer that cannot support that contract must refuse it.

Exact number literals (0064, PR #641) take the next version, v11, at admission, not by this record alone. Enum member numbers (0065) take the version after exact number literals' version at their admission. Neither feature has a numbered claim yet. Future admission pull requests update the released table with their publishing merge rather than leaving published versions marked unreleased.
